# Отчёт о работе системы: производительность, безопасность и проверка кода

Дата проверки: 7 октября 2026 года. Объект проверки: клиентская и серверная части приложения.

Production-сборка приложения успешно проходит автоматические проверки. Основные страницы используют серверную отрисовку и предварительную генерацию HTML. Персональные данные доступны через защищённые административные API. Для контроля качества предусмотрены статический анализ, проверка типов, автоматические тесты и форматирование кода.

Результаты относятся к локальной production-сборке. Проверка внешнего хостинга, действующего SSL-сертификата, подключения к рабочей PostgreSQL и реальной отправки писем в эти результаты не входит.

## 9.1. Производительность

### Первая отрисовка страниц

FCP — время до первой отрисовки содержимого страницы. Целевое значение составляет до 2 секунд. В локальной production-сборке все 36 измерений шести основных страниц соответствуют этому значению.

В таблице указаны медиана и максимальное время из трёх прогонов для каждой страницы, в секундах.

| Страница | 4G: медиана / максимум | Бытовой интернет: медиана / максимум |
| --- | --- | --- |
| `/` | 0.788 / 0.796 | 0.232 / 0.240 |
| `/about` | 0.652 / 0.656 | 0.192 / 0.216 |
| `/services` | 0.704 / 0.716 | 0.208 / 0.212 |
| `/contacts` | 0.596 / 0.608 | 0.180 / 0.180 |
| `/equipment` | 0.716 / 0.732 | 0.212 / 0.216 |
| `/pricing` | 0.684 / 0.688 | 0.204 / 0.216 |

Измерение выполняется в Chromium с выключенным браузерным кэшем и отдельным новым контекстом для каждого прогона. Профиль 4G использует скорость загрузки 9 Мбит/с, отправки 1,5 Мбит/с, задержку 80 мс, замедление CPU ×4 и мобильный экран 390×844. Профиль бытового интернета использует 50/10 Мбит/с, задержку 20 мс, CPU ×1 и экран 1440×900.

Ограничения сети задаются через Chrome DevTools Protocol. Каждый прогон включает контрольный HTTP-запрос для подтверждения задержки. При отсутствии подтверждения сценарий прекращает измерение. Команда запуска: `npm run analyze`. Результаты сохраняются в JSON; при медиане FCP выше 2000 мс команда завершается с ошибкой.

Сохранённые результаты: [performance-results.json](audit/performance-results.json).

Условия измерения: backend работает с изолированными тестовыми данными, запросы аналитики GTM/Google Analytics/Roistat/Яндекс.Метрики блокируются, серверный кэш может быть прогрет. Внешние CDN, DNS, TLS и cold start хостинга не воспроизводятся. Поэтому выполнение целевого FCP на опубликованном сайте подтверждается отдельным измерением на его HTTPS-домене. FCP не характеризует полную загрузку страницы или LCP.

### Изображения

Next Image выполняет оптимизацию поддерживаемых изображений и предоставляет форматы AVIF/WebP. Используются качества 75/85/95, параметры размеров и список разрешённых внешних источников. Изображение первого экрана загружается с приоритетом; некритичные изображения используют lazy-loading.

Для внешнего источника вне разрешённого списка SafeImage использует обычный img с lazy-loading и асинхронным декодированием. Автоматическое преобразование такого изображения в AVIF/WebP выполняется после настройки разрешённого источника.

Backend принимает растровые изображения с проверкой MIME, расширения и сигнатуры файла. HEIC декодируется и преобразуется в JPEG. Локальная загрузка через Next нормализует изображение в WebP с помощью sharp.

### SSR, SSG и кэширование

Главная страница, /about, /services, /contacts, /equipment и /pricing имеют заранее сформированный HTML. Заголовок h1 присутствует в серверном ответе до выполнения клиентского JavaScript.

Главная, /news, /portfolio и каталоги используют обновление публичных данных с интервалом 60 секунд. Карточки статьи и контроллера рендерятся сервером по запросу. Блок статей главной работает как серверный компонент; публичные запросы используют кэширование и таймауты. Production-сборка успешно завершает генерацию 74 страниц. Roistat загружается после основной загрузки страницы.

## 9.2. Безопасность

### Авторизация и доступ к персональным данным

Административные коллекции, список заявок, статистика и экспорт доступны только после авторизации. Публичные API каталогов возвращают разрешённый опубликованный контент. Публичный POST заявки проверяет формат, длины полей и согласие, сохраняет данные параметризованным SQL-запросом и возвращает только идентификатор и дату создания.

Backend использует HS256 JWT со сроком действия 24 часа. При обработке приватного запроса проверяются подпись, срок действия, issuer, audience, adminId и наличие администратора в базе.

В браузере основной токен хранится в HttpOnly cookie с SameSite=Strict и Secure в production. HttpOnly ограничивает доступ JavaScript к cookie. При выходе cookies удаляются. Полный отзыв ранее выданных JWT выполняется ротацией JWT_SECRET.

Для прямой загрузки файла используется отдельный токен на 2 минуты, разрешающий только POST /api/admin/upload/image. Такой токен не предоставляет доступ к персональным данным и остальным административным API.

Регистрация нового администратора доступна авторизованному администратору. Первое создание и административный сброс пароля выполняются через CLI backend. Секреты подписи задаются в конфигурации и должны содержать не менее 32 байт.

### Пароли и логирование

Backend хранит пароли в виде bcrypt-хешей с cost 12. Локальный файловый режим frontend использует scrypt со случайной солью и сравнение хешей с постоянным временем. Пароли не сохраняются в открытом виде в хранилище пользователей.

Обработчики авторизации и серверных ошибок не выводят пароли, хеши, токены или тело запроса. Клиент получает общее сообщение при серверной ошибке; диагностическое логирование ограничивается безопасными атрибутами ошибки. На хостинге access-логи также должны исключать Authorization, Cookie и содержимое запросов с персональными данными.

### Защита запросов и содержимого

React экранирует динамический текст при рендеринге. Frontend использует nosniff, запрет встраивания в iframe, политики referrer/permissions и базовую CSP. Внешние ссылки с target=_blank используют rel=noopener noreferrer. Текущая CSP ограничивает object, base, frame и form; строгая политика script-src с nonce/hash в данной конфигурации не используется.

CSRF-защита frontend проверяет Origin и признаки cross-site запроса при операциях изменения данных. Backend разрешает browser origins из CORS_ORIGINS; приватные запросы дополнительно требуют Bearer-авторизацию.

SQL-запросы передают пользовательские значения через параметры. Имена таблиц и изменяемых полей выбираются из разрешённого списка. Размеры выборок и длины поисковых запросов ограничены. При CSV-экспорте значения с формульными префиксами экранируются как текст.

Backend использует Helmet и Cache-Control: no-store для административных ответов. Лимиты запросов ограничивают частоту входа и отправки заявок. JSON, urlencoded и multipart имеют ограничения размера и количества частей. Загрузка SVG/HTML под видом растрового изображения отклоняется.

Для PostgreSQL TLS предусмотрена проверка сертификата и возможность указать собственный CA. Фактический режим соединения зависит от конфигурации окружения; локальное соединение через PG* без PGSSL может работать без TLS.

### HTTPS

TLS завершается на хостинге или reverse proxy. Пример [nginx.example.conf](nginx.example.conf) предусматривает перенаправление HTTP на HTTPS, TLS 1.2/1.3 и проксирование клиентской и серверной частей. Production frontend использует Secure cookies, HSTS и upgrade-insecure-requests.

Сертификат предоставляется или настраивается на стороне хостинга/заказчика. Для развёртывания задаются домены, пути сертификатов, HTTPS-адреса API_BASE_URL/PUBLIC_BASE_URL, разрешённые APP_ORIGINS/CORS_ORIGINS и доверенная конфигурация proxy. Внутренние порты приложения должны быть закрыты для прямого внешнего доступа.

Порядок настройки описан в [DEPLOYMENT.md](DEPLOYMENT.md). Действующий сертификат и перенаправления на целевом сервере проверяются после развёртывания.

## 9.3. Проверка кода

### Инструменты и результаты

ESLint выполняет статический анализ в обоих проектах. Frontend дополнительно проходит TypeScript-проверку без генерации выходных файлов. Prettier используется для форматирования защитных модулей и сценариев; команда format позволяет форматировать исходники.

| Проверка | Frontend | Backend |
| --- | --- | --- |
| ESLint | 0 ошибок, 59 предупреждений | Пройдено, без ошибок |
| TypeScript | typecheck пройден | JavaScript; отдельный typecheck не требуется |
| Unit / regression | 16 из 16 | 12 из 12 |
| e2e | 4 из 4 | 5 из 5 |
| Build | Production-сборка Next успешно выполнена в e2e/analyze | Проверка синтаксиса JS пройдена |
| npm audit | 0 известных уязвимостей на дату проверки | 0 известных уязвимостей на дату проверки |

Всего успешно пройдено 37 тестов, проваленных тестов нет. Предупреждения ESLint frontend относятся к неиспользуемым переменным, рекомендациям по img и зависимостям hooks.

Frontend e2e проверяет серверный HTML, навигацию, ограничения административного доступа, cross-origin запросы, вход и выход с HttpOnly cookie, создание заявки и защиту её данных. Backend тесты проверяют JWT, авторизацию, параметризацию SQL, хеширование паролей, CSV, загрузку изображений, HEIC, права upload-токена и rate limit входа.

Тесты используют изолированные данные без подключения к рабочей базе и реальной отправки писем. Подключение PostgreSQL и доставка писем проверяются отдельно в целевом окружении. Снимок аудита зависимостей: [dependency-audit.json](audit/dependency-audit.json).

Исходный код, конфигурация и автоматические проверки доступны для code review и security review со стороны заказчика. Документация предусматривает проверку критических замечаний перед выпуском; сроки их обработки определяются договорённостью сторон.

## Условия эксплуатации

Rate limit работает в памяти процесса. При нескольких репликах требуется общее хранилище ограничений и соответствующая настройка CDN/WAF. Файловый режим администрирования использует постоянное защищённое хранилище; runtime-файлы не предназначены для Git или публичной раздачи.

Приёмка на хостинге включает FCP на реальном HTTPS-домене с рабочими данными, сертификат и redirect, подключение к базе, доставку заявок и загрузку файлов через целевой proxy. Локальные результаты подтверждают работу перечисленных механизмов в проверенном окружении.
